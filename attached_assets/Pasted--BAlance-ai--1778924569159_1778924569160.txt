Провели масштабное обновление концепции продукта BAlance.ai. Теперь сервис работает как универсальный генератор проектной документации для ЛЮБЫХ типов бизнес-данных (не только CRM), создавая полную спецификацию требований и сравнительный анализ процессов.

Полностью перепиши логику в main.py по следующим требованиям:

1. УНИВЕРСАЛЬНЫЙ АНАЛИЗ ДАННЫХ (Любые таблицы):
- Удали из кода жесткую привязку к словам 'stage' или 'CRM'. Python должен просто считывать названия колонок, количество строк и вычислять базовую статистику (типы данных, заполненность, уникальные значения в текстовых колонках).
- Формируй универсальный контекст для ИИ: "Передана таблица бизнес-процесса. Колонки: {columns_str}. Объем: {total_rows} строк."

2. РЕНДЕРИНГ ДВУХ РАЗВЕРНУТЫХ BPMN СХЕМ (As-Is и To-Be):
- Обнови HTML-интерфейс страницы результатов: теперь там должно быть два графических контейнера: `<div id="canvas_as_is"></div>` и `<div id="canvas_to_be"></div>`.
- В коде Python создай два расширенных XML-шаблона BPMN. Каждая схема должна состоять минимум из 4-5 последовательных шагов (с пулами/дорожками, если применимо).
- Шаблон As-Is: Отражает текущий ручной/неэффективный процесс.
- Шаблон To-Be: Отражает целевой автоматизированный процесс.
- Заставь Groq (llama-3.1-8b-instant) возвращать массив из 8-10 названий шагов (первые 4-5 для As-Is, остальные для To-Be), которые Python через f-строки подставит в соответствующие XML-каркасы с жестко сохраненными координатами и стрелками.

3. ПОЛНАЯ СПЕЦИФИКАЦИЯ ТРЕБОВАНИЙ (По уровням):
- Измени системный промпт для Groq. ИИ должен генерировать текстовую спецификацию строго по четырем уровням требований:
  * Бизнес-требования (Business Requirements): Глобальные цели компании, бизнес-эффект, метрики успеха (As-Is vs To-Be).
  * Пользовательские требования (User Requirements): Use Case по Коберну (Предусловия, Сценарий взаимодействия Актора и Системы по шагам, Расширения, Постусловия).
  * Функциональные требования (Functional Requirements): Что конкретно должна делать система (валидация данных, интеграции, авто-уведомления).
  * Нефункциональные требования (Non-Functional Requirements): Производительность, безопасность, доступность, требования к интерфейсу.

4. РАЗДЕЛ 3: МАТРИЦА ТРАССИРОВКА И ПРИОРИТИЗАЦИИ (RTM):
- Добавь на страницу результатов третью вкладку/блок. ИИ должен сгенерировать таблицу Матрицы трассировки (Traceability Matrix).
- Колонки таблицы: ID требования | Тип требования | Описание фичи | Приоритет по методологии MoSCoW (Must / Should / Could).

Убедись, что кастомные CSS-стили в стиле Airbnb корректно отображают новые блоки, две схемы центрируются во вьюерах, а код не содержит синтаксических ошибок. Сделай коммит и отправь (push) в GitHub.
